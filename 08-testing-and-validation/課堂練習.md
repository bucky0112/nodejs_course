# 課堂練習：自己補齊沒測到的情境

> 這不是工作坊的延伸，而是**把這堂的核心重點再走一遍**，但這次沒有逐步指引，你得自己寫。
>
> 核心重點：把規格寫成測試；每個測試都要檢查狀態碼和回應內容；寫完用「故意改壞」確認它真的有在檢查。

工作坊的測試還有幾個情境沒涵蓋到。這個練習**不用 AI**，自己寫。

---

## 任務

在 `tests/` 裡補上下面這些情境的測試（加在既有的檔案裡，或另開一個 `tests/extra.test.js`）：

| # | 情境 | 預期 |
|---|---|---|
| 1 | `GET /todos?completed=false` | 200，每一筆的 `completed` 都是 `false` |
| 2 | `PATCH /todos/1` 送 `{ "title": "" }` | 400 |
| 3 | `PATCH /todos/1` 送 `{}` | 400，`error` 是 `沒有提供要更新的欄位` |
| 4 | `PATCH /todos/1` 送 `{ "title": "  改名  " }` | 200，`title` 是 `改名`（前後空白被去掉） |
| 5 | `POST /notes` 送 `{ "text": "重要", "pinned": true }` | 201，`pinned` 是 `true` |
| 6 | `DELETE /notes/:id` 成功時 | 204，而且回應**沒有 body** |
| 7 | `GET /不存在的路徑` | 404，回應是 JSON，`error` 裡有這個路徑 |

**明確規格**（這幾條就是這堂重點，別漏）：

- 每個測試都要檢查**狀態碼**，也要檢查**回應內容**（第 6 題檢查 body 是空的也算）。
- 每個測試都不能依賴其他測試留下的資料。需要資料就在測試裡自己新增。
- 每寫完一個測試，**故意改壞對應的程式碼**，確認它會失敗，再改回來。
- 不准修改 `src/` 底下的程式碼來讓測試通過。如果你覺得程式的行為不對，寫下來，不要改。

> 💡 不知道怎麼檢查「沒有 body」，先用 `console.log(res.body, res.text)` 看看 204 回應裡有什麼。不要翻完成版的測試照抄：憑記憶寫，寫不出來才回去看，這樣才練得到。

---

## 進階（行有餘力）

- 第 2、3 題的測試長得很像。試著用 `it.each` 把「PATCH 送了不合規格的資料都回 400」寫成一個表格式的測試。
- 想想：如果第 4 題失敗了，是程式錯還是規格錯？誰應該決定？

```bash
npm test
```

- [ ] 1. 七個情境都有測試，`npm test` 全部通過

- [ ] 3. 把測試的執行順序打亂（例如只跑其中一個：`npx vitest run -t "沒有 body"`）也會通過
- [ ] 4. 每個測試你都用「故意改壞」確認過會失敗
- [ ] 5. `src/` 沒有被修改
