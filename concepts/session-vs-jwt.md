# 概念卡：Session vs JWT

> 一句話：Session 把狀態存在**伺服器**（伺服器記得你）；JWT 把狀態放進**token**（伺服器不存，每次拿 token 來驗）。兩者各有取捨，沒有絕對贏家。

---

## 一、核心差異：狀態存在哪

| | Session | JWT |
|---|---|---|
| 狀態存哪 | **伺服器**（store 裡） | **token 裡**（伺服器不存） |
| 瀏覽器拿著 | 一個 sid（鑰匙） | 整個 token（含資料 + 簽名） |
| 認你的方式 | 用 sid 查伺服器的 store | 驗 token 的簽名 |

---

## 二、最關鍵的取捨：撤銷（revoke）

這是選擇時最該想清楚的一點：

- **Session 容易撤銷**：要讓某人立刻登出（密碼被盜、停權），伺服器把 store 裡那筆 session 刪掉就好，下次他的 sid 就查不到了。
- **JWT 難以撤銷**：token 一旦簽發，在**過期前都有效**，伺服器沒存它、也無法「收回」。改密碼、被盜、按登出，那個已發出的 token 仍然能用到過期。

> ⚠️ 所以「JWT 無狀態」是優點也是代價。很多教材只講「無狀態超棒、可橫向擴展」，卻不講「難撤銷」這個代價——這是不完整的。

要補救 JWT 的撤銷問題，得加額外機制：短期 access token + refresh token、或維護一個黑名單（但這樣又變回「有狀態」了）。

---

## 三、其他比較

| 面向 | Session | JWT |
|---|---|---|
| 多台伺服器 / 微服務 | 要共用 store（如 Redis） | 各服務有密鑰就能各自驗，較方便 |
| 伺服器負擔 | 每次要查 store | 只算簽名，不查庫 |
| 跨網域 / 行動 App | cookie 在跨網域較麻煩 | 帶 header 較通用 |
| 撤銷 / 登出 | 簡單 | 麻煩（見上） |
| 內容可見性 | sid 無意義 | payload 明文可讀（別放機密） |

---

## 四、怎麼選

- **單一後端、傳統網頁、要好控管登入狀態** → Session 很合適、也更安全好懂。
- **多服務 / 行動 App / 第三方要驗你的 token** → JWT 的無狀態有優勢。

> 本課程兩種都做過（[M5] Session、[M6] JWT），重點是理解取捨，而不是記「哪個比較好」。

## 延伸
- 兩者被竊取後都會被冒用（session hijacking / token 洩露），本質風險相近——別以為換成 JWT 就自動安全。
