# 第 8 堂工作坊：用測試驗證 API，也驗證 AI 的產出

第 7 堂審查 AI 的產出時，要一個一個 curl、一行一行看，很花時間。而且下次 AI 改了別的地方，你又要全部重打一次。這一堂把「打 API、看結果」寫成**測試程式**，之後一個指令就能全部驗證一遍。

流程：

```
裝好測試工具 → 親手替 /todos 寫測試 → 請 AI 替 /notes 寫測試 → 審查 AI 的測試 → 把「要寫測試」加進規則檔
```

## 步驟 0：為什麼寫測試

測試就是**把 API 對照表變成可以執行的程式**：

| API 對照表的一列 | 變成一個測試 |
|---|---|
| `GET /todos/:id` 找不到 → 404 | 發 `GET /todos/999`，檢查狀態碼是 404 |
| `POST /todos` 缺 title → 400 | 發 `POST /todos` 不帶 title，檢查狀態碼是 400 |

寫好之後，每次改程式（不管是你改的還是 AI 改的），跑一次 `npm test`，幾百毫秒就知道有沒有改壞。

> ⚠️ 測試不能取代看懂程式碼。測試只檢查**你寫下的情境**；沒寫到的情境，壞了也不會發現。而且要寫出好的測試，你得先知道程式**應該**怎麼運作。

---

## 步驟 1：裝好 vitest 和 supertest

```bash
npm install -D vitest supertest
```

- **vitest**：測試執行器，負責找出測試檔、執行、報告結果。
- **supertest**：對 Express app 發 HTTP 請求，**不需要真的開 port**。

`-D` 表示裝成 `devDependencies`：開發和測試時才需要，正式上線不用。

在 `package.json` 的 `scripts` 加上：

```json
"test": "vitest run",
"test:watch": "vitest"
```

還記得第 6 堂把 `app.js` 和 `server.js` 分開嗎？就是為了現在。測試程式 `import { app } from '../src/app.js'`，拿到組好的 app 但不 `listen`，supertest 直接把請求送進去。

最後，測試時不需要 morgan 印記錄，把 `src/app.js` 的 morgan 改成：

```js
// 跑測試時（vitest 會把 NODE_ENV 設成 'test'）不印請求記錄，輸出比較乾淨
if (process.env.NODE_ENV !== 'test') {
  app.use(morgan('dev'))
}
```

> ✅ **檢查點 A**：`npm test` 跑得起來（現在還沒有測試，會顯示找不到測試檔）。

## 步驟 2：第一個測試

建立 `tests/todos.test.js`：

```js
import { describe, it, expect } from 'vitest'
import request from 'supertest'
import { app } from '../src/app.js'

describe('GET /todos', () => {
  it('回傳 200 與陣列', async () => {
    const res = await request(app).get('/todos')

    expect(res.status).toBe(200)
    expect(Array.isArray(res.body)).toBe(true)
  })
})
```

逐行看：

- `describe('GET /todos', ...)`：把同一個路由的測試放在一組。
- `it('回傳 200 與陣列', ...)`：一個測試，描述寫「預期會發生什麼」。
- `await request(app).get('/todos')`：發請求，拿到回應。`res.status` 是狀態碼，`res.body` 是解析好的 JSON。
- `expect(實際值).toBe(預期值)`：檢查。不相等就算失敗。

```bash
npm test
```

> ✅ **檢查點 B**：看到 `1 passed`。

## 步驟 3：把 API 對照表的每一列都寫成測試

照第 5 堂的對照表，成功和失敗的情境都要寫。幾個例子：

```js
describe('GET /todos/:id', () => {
  it('找不到回 404 與錯誤訊息', async () => {
    const res = await request(app).get('/todos/999')

    expect(res.status).toBe(404)
    expect(res.body).toEqual({ error: '找不到這筆 todo' })
  })
})

describe('POST /todos', () => {
  it('新增成功回 201，回傳新的 todo', async () => {
    const res = await request(app).post('/todos').send({ title: '  寫測試  ' })

    expect(res.status).toBe(201)
    expect(res.body).toMatchObject({ title: '寫測試', completed: false })
    expect(res.body.id).toEqual(expect.any(Number))
  })

  it('壞掉的 JSON 回 400', async () => {
    const res = await request(app)
      .post('/todos')
      .set('Content-Type', 'application/json')
      .send('{bad')

    expect(res.status).toBe(400)
    expect(res.body).toEqual({ error: '請求的 JSON 格式錯誤' })
  })
})

describe('DELETE /todos/:id', () => {
  it('刪除成功回 204，之後查不到', async () => {
    const created = await request(app).post('/todos').send({ title: '等一下就刪' })

    const res = await request(app).delete(`/todos/${created.body.id}`)
    expect(res.status).toBe(204)

    const after = await request(app).get(`/todos/${created.body.id}`)
    expect(after.status).toBe(404)
  })
})
```

幾個常用的檢查方式：

| 寫法 | 意思 |
|---|---|
| `toBe(201)` | 完全相等（數字、字串、布林） |
| `toEqual({ error: '...' })` | 物件內容完全相同 |
| `toMatchObject({ title: '寫測試' })` | 物件**至少**有這些欄位和值 |
| `expect.any(Number)` | 任何數字都可以（例如自動產生的 id） |

> 💡 刪除的測試自己先新增一筆再刪，不依賴其他測試留下的資料。每個測試都能單獨跑、順序打亂也不會壞，是好測試的特徵。

把列表、單筆、新增、更新、刪除的成功與失敗情境都補齊，參考 [`完成版/tests/todos.test.js`](./完成版/tests/todos.test.js)。

> ✅ **檢查點 C**：`tests/todos.test.js` 涵蓋對照表的每一種狀態碼，全部通過。

## 步驟 4：故意改壞，確認測試抓得到

**一個永遠不會失敗的測試，沒有用。**把 `src/controllers/todos.controller.js` 裡新增的 `res.status(201)` 改成 `res.status(200)`，再跑：

```bash
npm test
```

應該看到 `新增成功回 201` 這個測試失敗，並告訴你「預期 201，實際 200」。確認後改回 201。

以後每寫一個測試，都可以用這招確認它真的有在檢查東西。

> ✅ **檢查點 D**：改壞時對應的測試失敗，改回來全部通過。

## 步驟 5：請 AI 替 /notes 寫測試，再審查它的測試

你已經親手寫過一次，知道好的測試長什麼樣，現在可以請 AI 幫忙了：

```
請替 /notes 寫測試，放在 tests/notes.test.js，用 vitest + supertest，
參考 tests/todos.test.js 的寫法。API 對照表：
（貼上第 7 堂的 /notes 對照表）
每一種狀態碼至少一個測試，每個測試都要檢查狀態碼和回應內容。
```

AI 寫完後，**審查它的測試**，這比審查一般程式碼更需要小心：

1. **對照表的每一列都有測試嗎？** 特別看 404 和 400。
2. **每個測試都有 `expect` 嗎？** 只發請求、沒有檢查的測試永遠會通過。
3. **預期值是規格，還是抄程式目前的行為？** 如果程式本來就有錯（例如新增回 200），AI 可能寫出「預期 200」的測試，把錯誤當成正確。拿對照表比對，不要拿程式碼比對。
4. **用步驟 4 的方法**，挑兩三個測試改壞程式，確認它們會失敗。

> ✅ **檢查點 E**：`tests/notes.test.js` 通過審查，每個測試你都說得出它在檢查什麼，`npm test` 全部通過。

## 步驟 6：請 AI 審查程式碼，並把測試加進規則

最後兩件事：

**1. 請 AI 依規則審查。**

```
請依照 AGENTS.md 審查 src/ 底下 notes 相關的三個檔案，
列出違反規則的地方（附規則編號），不要直接修改。
```

AI 列出的每一條，你都要判斷：真的違反規則嗎？規則有沒有這樣寫？有些建議看起來合理，但規則沒要求，例如「加上 zod 做驗證」，就要退回（違反「不要加新套件」）。

**2. 把「要寫測試」加進 `AGENTS.md`。**

在「完成之後」前面新增一段「測試」，內容見 [`完成版/AGENTS.md`](./完成版/AGENTS.md) 的第 17–19 條，並把最後一條改成「執行 `npm test` 並貼上結果」。

以後請 AI 加新功能，它要附上測試；你跑 `npm test` 確認全過，再加上審查，才採納。

> ✅ **檢查點 F（完成版）**：`npm test` 全部通過，`AGENTS.md` 有測試相關規則。你的專案應該跟 [`完成版/`](./完成版/) 一致。
