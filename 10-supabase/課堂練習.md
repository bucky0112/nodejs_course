# 課堂練習：寫一條 RLS policy，讓使用者只能讀到自己的資料

> 這章最關鍵、也最容易出包的不是 Realtime，而是 **RLS**——前端直接拿 publishable key 打資料庫時，唯一替你把關的就是這層。工作坊只「認識」了 RLS；這個練習要你**親手寫、親手驗**，確認它真的擋得住。
>
> 工作坊步驟 4 給過一條 SELECT policy 的長相。**這次請不要照抄**——憑理解自己寫，寫不出來才回去翻概念卡，這樣才練得到。

---

## 任務

在 Supabase 後台的 **SQL Editor** 裡，對 `todos` 表（每筆有一個 `user_id` 欄）做到下面這些。整段不超過十幾行 SQL，但每一條都對應一個你必須搞懂的點。

**要做到的事**：

| # | 要求 |
|---|---|
| 1 | 對 `todos` **開啟** RLS。開啟後預設會發生什麼事，先想清楚再往下。 |
| 2 | 寫一條 **SELECT** policy：只有 `authenticated` 角色、且該列 `user_id` 等於目前登入者，才讀得到。 |
| 3 | 再寫一條 **INSERT** policy：登入者只能新增 `user_id` 是自己的列（別人不能借你的手塞資料給他自己）。 |

**明確規格**（這幾條就是 RLS 的重點，別漏）：

- 開 RLS 用 `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`。
- 「目前登入者是誰」用 Supabase Auth 提供的函式取得，對應 `todos.user_id`。
- INSERT policy 要管的是「**寫進去的新列**」長什麼樣，這跟 SELECT 用來篩「**已存在的列**」的子句**不是同一個**——想清楚各自該用哪個。
- 每條 policy 都明確限定只給 `authenticated` 角色，別不小心也放行 `anon`。

> 💡 卡在「SELECT 跟 INSERT 的條件子句為什麼不一樣」時，回去翻 [概念卡：Supabase RLS](../concepts/supabase-rls.md)。憑記憶寫，別翻工作坊那段照抄。

## 觀念題（用文字作答）

某同學說：「我的 publishable key 直接寫死在前端 JS 裡，被人從瀏覽器 F12 抄走了，這下完蛋，要趕快換 key。」

請用 2~3 句話回答：**在「RLS 有設好」的前提下，publishable key 外洩到底要不要緊？為什麼？** 順便說說：如果外洩的是 **secret key**，又為什麼是完全不同等級的災難？

> 提示：回想概念卡那張表——哪把金鑰**會**被 RLS 限制、哪把**不會**？

---

## 進階（行有餘力）

- 再補 **UPDATE** 與 **DELETE** 兩條 policy，讓「改／刪」也只限自己的列。想想 UPDATE 同時牽涉「能改哪些舊列」跟「改完後的新列長怎樣」兩面。
- 把這四條 policy 整理成一段可重跑的 SQL（重跑前先 `DROP POLICY IF EXISTS`），這樣 demo 給別人看時不會因為「policy 已存在」報錯。

## 自我檢核

RLS 不能只靠「SQL 跑過沒報錯」就算數——**一定要用兩種身分各查一次，看它真的擋住**。在 SQL Editor 或 supabase-js 裡這樣驗：

1. 準備兩個使用者 A、B（Authentication → Users 各建一個），並各自塞一兩筆 `user_id` 是自己的 `todos`。
2. **以 A 的身分**查 `select * from todos`：應只看到 A 自己的列，看不到 B 的。
3. **以 B 的身分**查同一句：應只看到 B 自己的列。
4. **以 `anon`（沒登入）身分**查：應一列都讀不到。
5. 試著**以 A 的身分** insert 一筆 `user_id` 指向 **B** 的 todo：應被 policy 擋下（INSERT 失敗）。

> 用 SQL Editor 時可用 `set role authenticated;` 搭配設定 `request.jwt.claims` 來模擬登入身分；用 supabase-js 時則各自帶 A／B 的 access token 發查詢。任一方式能重現「看得到自己、看不到別人」即可。

- [ ] 1. 對 `todos` 開了 RLS（且你說得出「開了之後預設是全擋」）
- [ ] 2. A 只查得到自己的列，查不到 B 的
- [ ] 3. B 只查得到自己的列，查不到 A 的
- [ ] 4. 沒登入（`anon`）一列都讀不到
- [ ] 5. A 不能 insert `user_id` 是 B 的列（INSERT policy 真的擋住）
- [ ] 6. 觀念題你寫得出「RLS 有設好 → publishable key 外洩不致命；secret key 繞過 RLS → 外洩等於資料庫全開」

> 前五條都驗出「擋住」、加上答得出觀念題，代表你抓到了 Supabase 前端直連安全最核心、也最常被寫漏的那一點。
