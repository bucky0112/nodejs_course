## 步驟 0：為什麼舊的測試不能直接用

第 8 堂的測試假設資料在記憶體裡：每次啟動都有一筆 id 1 的 todo。接上資料庫之後：

- 資料庫裡有什麼資料，每個人、每次都不一樣，測試結果就不穩定。
- 測試會新增、刪除資料。直接跑在開發用的 `todo_app` 上，會把你手動建的資料弄亂。

解法：**準備一個測試專用的資料庫，每個測試開始前清空，需要的資料由測試自己建立。**

---

## 步驟 1：建立測試資料庫

```bash
createdb todo_app_test
npm install -D vitest supertest
```

在 `package.json` 的 `scripts` 加回 `"test": "vitest run"` 和 `"test:watch": "vitest"`。

建立 `.env.test`，指向測試資料庫，並加進 `.gitignore`：

```bash
DATABASE_URL="postgresql://你的使用者名稱@localhost:5432/todo_app_test"
```

一樣建一個 `.env.test.example` 放格式範例。

> ⚠️ `.env.test` 千萬不要指向 `todo_app`。測試每次都會清空資料表。

---

## 步驟 2：讓測試自動用測試資料庫

需要三個檔案。

**`tests/load-test-env.js`**：讀 `.env.test`，把 `DATABASE_URL` 換成測試資料庫。

```js
import { config } from 'dotenv'

const { error } = config({ path: '.env.test', override: true })
if (error) {
  throw new Error('找不到 .env.test：請複製 .env.test.example 成 .env.test，並設定測試資料庫的 DATABASE_URL')
}
```

`override: true` 讓它蓋過 `.env` 的設定。之後 `src/db/prisma.js` 裡的 `import 'dotenv/config'` 不會覆蓋已經存在的環境變數，所以 app 連的就是測試資料庫。

**`tests/global-setup.js`**：跑全部測試之前執行一次，把 migration 套用到測試資料庫。

```js
import { execSync } from 'node:child_process'
import './load-test-env.js'

export default function setup() {
  execSync('npx prisma migrate deploy', { stdio: 'inherit', env: process.env })
}
```

`migrate deploy` 只套用既有的 migration、不產生新的，適合測試和正式環境。

**`tests/setup.js`**：每個測試檔執行前載入，每個測試開始前清空資料表。

```js
import './load-test-env.js'
import { beforeEach, afterAll } from 'vitest'
import { prisma } from '../src/db/prisma.js'

beforeEach(async () => {
  await prisma.$executeRawUnsafe('TRUNCATE todo_tags, todos, lists, tags RESTART IDENTITY CASCADE')
})

afterAll(async () => {
  await prisma.$disconnect()
})
```

`TRUNCATE ... RESTART IDENTITY` 清空資料表，id 也從 1 重新開始。這是測試專用的工具，所以用了一行原生 SQL。

最後在專案根目錄建立 `vitest.config.js`，把它們串起來：

```js
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    globalSetup: ['./tests/global-setup.js'],
    setupFiles: ['./tests/setup.js'],
    // 所有測試檔共用同一個測試資料庫，一次只跑一個檔，避免互相清掉對方的資料
    fileParallelism: false,
  },
})
```

> ✅ **檢查點 A**：`npm test` 會先印出套用 migration 的訊息。這時舊的測試大多會失敗（因為資料庫是空的），這是預期中的。

## 步驟 3：改寫測試，讓每個測試自己準備資料

建立 `tests/helpers.js`，透過 API 建立資料：

```js
import request from 'supertest'
import { app } from '../src/app.js'

export async function createTodo(body = {}) {
  const res = await request(app).post('/todos').send({ title: '測試用 todo', ...body })
  return res.body
}

export async function createList(name = '工作') {
  const res = await request(app).post('/lists').send({ name })
  return res.body
}

export async function createTag(name = '急件') {
  const res = await request(app).post('/tags').send({ name })
  return res.body
}
```

然後把依賴「id 1 一定存在」的測試改成先建立資料：

```js
// 改寫前：假設 id 1 存在
const res = await request(app).patch('/todos/1').send({ completed: true })

// 改寫後：自己建立，用回傳的 id
const todo = await createTodo()
const res = await request(app).patch(`/todos/${todo.id}`).send({ completed: true })
```

再替第 12 堂的清單和標籤補上測試（`tests/lists-and-tags.test.js`）。這一步**自己寫**，參考 [`完成版/tests/`](./完成版/tests/)。

`notes.test.js` 不用改，notes 還在記憶體裡。

> ✅ **檢查點 B**：`npm test` 全部通過；在開發資料庫 `todo_app` 手動新增的資料，跑完測試後還在。

## 步驟 4：規則檔加上資料層規則

第 7、8 堂的 `AGENTS.md` 還寫著「資料存在記憶體、不要接資料庫」，已經不對了。更新它：

1. 「技術選擇」改成 Node 22.18、Prisma 7 + PostgreSQL，說明哪些資料在資料庫、notes 還在記憶體。
2. 狀態碼表加上 409；id 的規則改成「資料庫的 id 交給資料庫產生」。
3. 新增一段「資料層」：

| 規則 | 來自 |
|---|---|
| 資料表結構只能透過 schema + migration 修改，不准 `db push`、不准直接改表 | 第 11 堂 |
| 不准修改已經存在的 migration 檔 | 第 11 堂 |
| 只能從 `src/db/prisma.js` 匯入 `prisma`，而且只有 service 可以匯入 | 第 6、11 堂 |
| 用 Prisma Client 查詢，不寫原生 SQL | 第 11 堂 |
| 可預期的資料庫錯誤要先檢查，拋 404 / 400 / 409，不能變成 500 | 第 12 堂 |
| 改 model 時說明 migration 的 SQL，確認既有資料不會遺失 | 第 9–12 堂 |

4. 「測試」那一條補上：測試連 `.env.test` 的資料庫、每個測試前會清空、需要的資料自己建立。

完整內容見 [`完成版/AGENTS.md`](./完成版/AGENTS.md)。跟第 7 堂一樣，**每一條你都要知道是哪一堂學的**。說不出來的規則，你就沒辦法審查 AI 有沒有遵守。

> ✅ **檢查點 C**：`AGENTS.md` 有「資料層」一段，每一條都說得出來源。

## 步驟 5：請 AI 加上「優先順序」功能

需求：todo 要有優先順序。

```
請依照 AGENTS.md 的規則，替 todo 加上優先順序 priority。

規格：
- priority 只能是 low、medium、high 其中之一，預設 medium
- 既有的 todo 套用 migration 後要是 medium
- POST /todos、PATCH /todos/:id 可以帶 priority，值不合法回 400
- GET /todos?priority=high 只回傳該優先順序的 todo，值不合法回 400
- GET /todos、GET /todos/:id 的回應要有 priority

請產生 migration（名稱 add_todo_priority），並在 tests/ 補上測試。
完成後說明 migration 產生了哪些 SQL，執行 npm test 並貼上結果。
```

**先不要採納**，進到下一步審查。

> ✅ **檢查點 D**：AI 產生了程式碼、migration 和測試，並說明了 migration 的 SQL。

## 步驟 6：審查

這次的審查比第 7 堂多了資料層。用 `git status`、`git diff` 看 AI 改了什麼，照這個順序檢查：

**1. schema 與 migration**

- `schema.prisma` 怎麼表示「只能是三個值之一」？（Prisma 的 `enum`）預設值有沒有設？
- 打開新的 `migration.sql`：是不是 `CREATE TYPE` 加上 `ALTER TABLE ... ADD COLUMN ... DEFAULT 'medium'`？有沒有任何 `DROP`？
- 有沒有改到**舊的** migration 檔？（違反規則）
- 用 `psql -d todo_app -c '\d todos'` 確認欄位真的加上了，既有的 todo 都是 `medium`。

**2. service、controller、routes**

- 驗證寫在 service 嗎？`?priority=` 的值不合法時，是 400 還是讓 Prisma 報錯變成 500？
- controller 只多傳了一個 query 參數嗎？
- 有沒有出現 `$queryRaw`、`new PrismaClient()`、新套件？

**3. 測試**

- 每一條規格都有測試嗎？特別是「預設 medium」和兩種 400。
- 測試有沒有自己建立資料，而不是假設某個 id 存在？
- 用第 8 堂的方法，故意把預設值改成 `low`，看測試會不會失敗。
- 有沒有**改了既有測試的預期結果**？（違反規則）

**4. 看不懂的地方**

有任何一行說不出它在做什麼，就問 AI，搞懂之前不採納。

把結果寫成審查表：

| 檔案 | 違反哪一條規則／有什麼問題 | 採納、修改還是退回 | 理由 |
|---|---|---|---|
| | | | |

有問題就指出規則編號請 AI 修正，再審查一次。

> ✅ **檢查點 E**：審查表完成，每個採納的地方都說得出它在做什麼。
