# 課堂練習：從零照三層長出一個新資源

> 這不是工作坊的延伸，而是**把這章的核心重點再走一遍**——但這次沒有逐步指引，你得自己決定「哪段程式碼該放在哪一層」。
>
> 核心重點：**三層職責切分**——routes 只宣告路徑、controller 只碰 HTTP、service 才碰驗證與資料庫。

工作坊帶你把現成的 `app.js` 拆成 routes / controllers / services 三層。現在你要在**同一個專案**裡，從零長出一個全新的資源 `notes`（筆記），整套——schema、service、controller、routes、掛載——都得你自己照三層擺好。

> ⚠️ 這題不考「會不會寫 CRUD」，考的是**每一段程式碼有沒有放對層**。寫的時候每打一行就問自己一句：「這行屬於 HTTP、屬於商業邏輯，還是只是宣告路徑？」放錯層就算功能會動也不算過。

---

## 任務

### 0. 先補一張表（`src/db/schema.js`）

完成版的 schema 目前只有 `lists`、`todos`、`tags`、`todoTags`，**沒有 `notes` 表**。先自己加上：

- 新增 `notes` 表：`id`（`integer().generatedAlwaysAsIdentity().primaryKey()`）、`content`（`varchar`，必填）。
- 產生並套用 migration（`npm run generate` / `npm run migrate`）。

> notes 跟其他表沒有關聯，所以**不用寫 `relations()`**——這題的重點不在關聯，在分層。

### 1. service（`src/services/notes.service.js`）

這一層**只碰商業邏輯與資料庫**，碰不到 `req` / `res`。照工作坊裡 `tags.service.js`、`todos.service.js` 的樣子寫：

- `listNotes()`：回傳所有 notes。
- `createNote({ content })`：`content` 缺或空字串 → `throw new HttpError(400, ...)`；否則寫入並回傳新筆記。
- `getNote(id)`：找不到 → `throw new HttpError(404, ...)`。
- `deleteNote(id)`：刪除；刪不到（id 不存在）→ `throw new HttpError(404, ...)`。

> service 不知道「HTTP 狀態碼」這回事，它只會「拋一個帶 status 的錯誤」。把狀態碼塞進 `HttpError`，剩下交給 `errorHandler`。

### 2. controller（`src/controllers/notes.controller.js`）

這一層**只負責 HTTP**：讀 `req`、呼叫 service、決定狀態碼、`res` 回去。**維持裸 async，不要寫 try/catch**——Express 5 會自動把拋出的錯誤轉給 `errorHandler`（這正是本章為什麼能這樣寫的原因）。

- `list` → `200` + 陣列
- `create` → `201` + 新筆記
- `get` → `200` + 單筆（記得把 `req.params.id` 轉成 `Number`）
- `remove` → `204`、無 body

### 3. routes（`src/routes/notes.routes.js`）

這一層**只宣告路徑**，幾乎沒有邏輯——一條路徑對一個 controller function。

| 方法 | 路徑 | 對應 controller |
|---|---|---|
| GET | `/notes` | `list` |
| POST | `/notes` | `create` |
| GET | `/notes/:id` | `get` |
| DELETE | `/notes/:id` | `remove` |

### 4. 掛進總路由（`src/routes/index.js`）

把 `notesRouter` 用 `routes.use('/notes', notesRouter)` 掛上去，跟 `todos` / `lists` / `tags` 並排。

---

## 明確規格（這幾條就是這章的「放對層」驗收點，別漏）

- `POST /notes` 當 `content` 缺或為空字串 → 回 **400**。**這個判斷要寫在 service**，不是 controller。
- `GET /notes/:id` 查不到 → 回 **404**（service 拋 `HttpError`）。
- `DELETE /notes/:id` 成功回 **204**（無 body）；id 不存在回 **404**。
- **controller 不可直接 `import { db }` 打 DB**——資料庫只在 service 出現。
- **service 不可碰 `req` / `res`**——它只收乾淨參數、回乾淨資料或拋錯。
- controller **不寫 try/catch**，靠 Express 5 自動轉送錯誤。

> 💡 卡住時回去翻工作坊與 [概念卡：分層架構](../concepts/分層架構.md)。但**別把 `tags.*.js` 整段複製過來改名**——憑記憶照三層的職責自己擺，擺不出來才回去對照，這樣才練得到「東西該放哪一層」這件事。

## 進階（行有餘力）

- `createNote` 的驗證錯誤訊息也走 `HttpError`（你應該本來就是了）——再想一層：如果之後要支援「`content` 太長回 400」，這段該加在哪一層？（答案還是 service，因為那是商業規則。）
- 看著你寫好的 `notes.routes.js`：為什麼這個檔案幾乎沒有任何邏輯？把「路徑宣告」和「處理邏輯」分開，對日後加 middleware（例如登入檢查）有什麼好處？

## 自我檢核

把伺服器跑起來，用下面的 curl（或 REST Client / Postman）逐條打。**全過才算完成**：

```bash
# 1. 建一筆 note → 應回 201，回傳帶 id 與 content
curl -i -X POST localhost:3000/notes -H 'Content-Type: application/json' -d '{"content":"買牛奶"}'

# 2. content 缺 → 應回 400（且這個 400 是 service 拋的）
curl -i -X POST localhost:3000/notes -H 'Content-Type: application/json' -d '{}'

# 3. content 空字串 → 應回 400
curl -i -X POST localhost:3000/notes -H 'Content-Type: application/json' -d '{"content":""}'

# 4. 列出全部 → 應回 200 + 陣列
curl -s localhost:3000/notes

# 5. 查不存在的 id → 應回 404
curl -i localhost:3000/notes/999

# 6. 刪掉剛建的那筆（把 1 換成實際 id）→ 應回 204、無 body
curl -i -X DELETE localhost:3000/notes/1

# 7. 再刪同一筆 → 應回 404
curl -i -X DELETE localhost:3000/notes/1
```

- [ ] 1. 建 note 成功（`201`）
- [ ] 2. `content` 缺 → `400`
- [ ] 3. `content` 空字串 → `400`
- [ ] 4. `GET /notes` 回陣列（`200`）
- [ ] 5. 查不存在的 id → `404`
- [ ] 6. 刪除成功 → `204`、無 body
- [ ] 7. 重複刪除 → `404`

最後做一次「分層體檢」（這才是這題真正要驗的）：

- [ ] `notes.controller.js` 裡**沒有** `import` 任何 `db` / schema —— DB 只出現在 service
- [ ] `notes.service.js` 裡**沒有**出現 `req`、`res`、`res.status(...)` —— 它只回資料或拋 `HttpError`
- [ ] controller 的每個 function 都是**裸 async、沒有 try/catch**
- [ ] `notes.routes.js` 只有 `Router()` + 四行路徑宣告，沒有商業邏輯

> 七條 curl 全綠、四條分層體檢全打勾——代表你已經能把一個新資源**從零照三層職責擺對位置**，而不只是把 CRUD 寫得會動。
