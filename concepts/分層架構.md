# 概念卡：分層架構（為什麼要拆三層）

> 一句話：當單一檔案塞太多責任（路由、HTTP、驗證、DB），就把它**沿著責任切開**——route 管路徑、controller 管 HTTP、service 管業務邏輯與 DB。

---

## 一、架構光譜：不是「越分層越好」

把後端的組織方式想成一條光譜，從左到右，責任拆得越來越細：

```
單檔                 分層 / MVC               領域導向 / Clean / Hexagonal
(現在的 app.js)      (本課採用)               (大型、長壽、多人專案)
所有東西塞一起        route→controller→service  再切 domain/use-case/adapter…
```

- **單檔**：M1~M3 的 `app.js`——所有路由、驗證、DB 查詢全擠在一個檔。小專案下手最快，但檔案一長就難讀、難測、難改。
- **分層 / MVC**：把責任切成幾條清楚的水平層，每層只做一件事。**本課用的就是這層**——對一個 todo app 來說剛剛好。
- **領域導向 / Clean / Hexagonal**：再往細拆，把業務領域、用例、外部 adapter 都隔開。好處是超大型專案能撐很久；代價是檔案數爆增、繞來繞去。

> ⚠️ **誠實話**：架構是為了「管理複雜度」，不是越多層越高級。本課這種規模，**分層剛好**；硬套 Clean Architecture 反而是過度設計，徒增負擔。學會分層，知道光譜右邊「有這些東西、需要時再查」即可。

---

## 二、三層的職責邊界

拆三層的重點不在「多開幾個資料夾」，而在**每一層只准碰自己該碰的東西**。記住這張表，就抓到分層的精髓：

| 層 | 只做這些 | 絕對不碰 |
|---|---|---|
| **route** | 宣告「哪個路徑 + 哪個 method」對到哪個 controller 函式 | 任何邏輯、任何 `req`/`res` 細節 |
| **controller** | 碰 HTTP：讀 `req`（params/body）、設 status code、回 `res` | 不直接打 DB、不寫業務規則 |
| **service** | 業務邏輯 + 驗證 + DB 存取；回**純資料**或拋 `HttpError` | 不認識 `req`/`res`、不知道自己在跑 HTTP |

一句話記法：
- **route**：交通指揮——只指路，不做事。
- **controller**：翻譯員——把 HTTP 世界翻成 service 聽得懂的呼叫，再把結果翻回 HTTP。
- **service**：真正幹活的人——它不知道（也不該知道）外面是 HTTP 還是 CLI 還是測試在呼叫它。

這條邊界帶來的最大好處：**service 可以被單獨測試**。因為它只吃參數、回資料，不依賴 `req`/`res`，你不用起一個 HTTP 伺服器就能驗證業務邏輯。

## 三、為什麼 `app.js` 與 `server.js` 要分開

成品把啟動拆成兩個檔，這不是潔癖，是有用意的：

```js
// app.js —— 組裝：建立 app、掛 middleware、掛 routes，然後 export
export const app = express()
app.use(express.json())
app.use(routes)
// …不呼叫 listen

// server.js —— 啟動：把組好的 app 跑起來
import { app } from './app.js'
app.listen(PORT, ...)
```

- **`app.js` 負責「組裝」**：定義這個 app 由哪些 middleware、哪些路由構成，但不真的開 port。
- **`server.js` 負責「啟動」**：`import` 那個組好的 app，呼叫 `listen` 監聽 port。

分開的理由：**測試時你想要 app 但不想真的佔用 port**。測試框架（如 supertest）可以直接 `import { app }` 丟進去發請求，全程不開伺服器；正式跑才用 `server.js` 真正 `listen`。組裝與啟動一旦分離，同一個 app 就能服務「測試」和「上線」兩種場景。

## 四、controller 為什麼沒有 try/catch 也能處理錯誤

看成品的 controller，你會發現它是**裸 async 函式、完全沒有 try/catch**：

```js
export async function get(req, res) {
  res.json(await todosService.getTodo(Number(req.params.id)))
}
```

可是 service 裡 `throw new HttpError(404, ...)` 卻能正確變成 404 回應。為什麼？

因為 **Express 5 會自動接住 async handler 回傳的 rejected promise，幫你呼叫 `next(err)`**，把錯誤轉送到最後的 errorHandler。Express 4 沒有這個能力，你得在每個 controller 包 try/catch——這正是本課鎖定 Express 5 的好處之一。

→ 細節見 [概念卡：Express 的錯誤處理](./express-錯誤處理.md)

## 延伸
- 再往光譜右邊：Clean Architecture、Hexagonal（Ports & Adapters）、DDD。核心都是「把業務邏輯和外部細節隔開」，只是隔得更徹底。等專案大到「換 DB / 換框架」變成真實需求時再研究。
- service 回傳的資料若要再加工（隱藏欄位、改名），可以再拆出一層 **serializer**（見本章挑戰題）。
