# 課堂練習：親手寫 bcrypt 認證 + session 版 requireAuth

> 這章的核心重點不是「會 `npm install express-session bcrypt`」，而是**密碼只存雜湊（不存明文）、登入靠 bcrypt 比對、登入狀態靠 session 認人**。這個練習就針對這幾點。
>
> 工作坊已經給過註冊 / 登入 / `requireAuth` 的完整程式碼。**這次請不要翻完成版**——憑理解自己寫一遍，才知道哪裡其實沒搞懂。

## 題目 1：自己寫一個 session 版 `requireAuth`

把 `src/middleware/requireAuth.js` 清空，自己重寫一個。要求：

- 判斷登入狀態的依據是 **`req.session.userId` 有沒有值**（不是 header、不是 token）。
- 沒登入（`req.session.userId` 不存在）：回 **401**，附一段 JSON 錯誤訊息。
- 有登入：直接 `next()` 放行，**不要**在這裡查資料庫。

> 🧠 為什麼 cookie 裡只有一串 session id，伺服器就認得出你是誰？→ [概念卡：HTTP 無狀態與 Session 機制](../concepts/session-機制.md)

---

## 題目 2：自己寫註冊與登入（bcrypt 雜湊 / 比對）

把 `app.js` 裡的 `/auth/register` 與 `/auth/login` 清空，自己重寫。要求：

**`POST /auth/register`**

- 驗 `username`（字串、`trim` 後至少 3 個字）與 `password`（字串、至少 6 個字），不合格回 **400**。
- `username` 已存在回 **409**。
- 用 `bcrypt.hash`（cost factor 用 10）算出雜湊，**只把雜湊存進 `passwordHash`**——資料庫裡絕不能出現明文密碼。
- 把這位使用者的 id 寫進 session（註冊完直接登入），讓之後 `requireAuth` 認得出他。
- 回 **201**，body **只含 `id` 與 `username`**，不回 `passwordHash`。

**`POST /auth/login`**

- 用 `username` 撈出使用者，再用 `bcrypt.compare` 比對輸入密碼與存好的 `passwordHash`（**不能**用 `===` 比）。
- 「帳號不存在」與「密碼錯」要回**同一段 401 訊息**（不要洩漏哪個 username 存在）。
- 比對通過：把使用者 id 寫進 session，回使用者 `{ id, username }`。

---

## 題目 3：加一條受保護路由 `GET /me`

新增一條路由，讓登入者查「我是誰」：

- 掛上你題目 1 寫的 `requireAuth`。
- 用 `req.session.userId` 去資料庫撈使用者。
- 回 `{ id, username }`——**絕對不要**把 `passwordHash` 也回出去。

## 題目 4（觀念，用文字作答）

用 2~3 句話分別回答：

1. 為什麼資料庫存的是 `passwordHash` 而不是明文密碼？就算只是內部小專案，存明文會帶來什麼後果？
2. `bcrypt` 為什麼要「加鹽（salt）」？兩個人剛好設了一樣的密碼，存進去的雜湊會不會一樣，為什麼？

> 提示：想想資料庫外洩時，明文密碼 vs 雜湊密碼的差別；以及「同密碼 → 同雜湊」會讓攻擊者佔到什麼便宜。

## 自我檢核

用 **cookie jar**（`-c` 寫入、`-b` 帶上）模擬一個瀏覽器的登入狀態，逐條打、對照預期結果。**全過才算完成**：

```bash
# 1. 註冊一個帳號，並把 cookie 存進 jar → 應回 201，body 不含 passwordHash
curl -i -c jar.txt -X POST http://localhost:3000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"secret123"}'

# 2. 帶著 jar（已登入）打受保護路由 → 應回 200 + {id, username}
curl -i -b jar.txt http://localhost:3000/me

# 3. 不帶 jar（沒登入）打受保護路由 → 應回 401
curl -i http://localhost:3000/me

# 4. 用錯密碼登入 → 應回 401（且訊息和「帳號不存在」一樣）
curl -i -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"wrong-pass"}'

# 5. 用正確密碼登入，刷新 jar → 應回 200
curl -i -c jar.txt -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"secret123"}'
```

打完後，去資料庫看一眼 `users.password_hash` 那欄。

- [ ] 1. 註冊回 `201`，且回傳的 body **不含** `passwordHash`
- [ ] 2. 帶著 cookie jar 打 `/me` 回 `200` + `{id, username}`（不含 `passwordHash`）
- [ ] 3. 不帶 cookie 打 `/me` 回 `401`
- [ ] 4. 密碼錯回 `401`，且訊息與「帳號不存在」無法區分
- [ ] 5. 資料庫 `password_hash` 存的是 `$2b$...` 開頭的雜湊（**不是**明文 `secret123`）
- [ ] 6. 題目 4 你寫得出「明文外洩等於直接送出帳密」「加鹽讓同密碼也產生不同雜湊」這兩層意思

> 五條 curl 全綠 + 資料庫存的是雜湊 + 答得出題目 4，代表你抓到了 session 認證最核心、也最容易被做錯的那幾點。
