# 課堂練習：state 防 CSRF——說清楚攻擊、補上驗證

> 這章的核心重點不是「會串 Google 登入」，而是 OAuth 授權碼流程裡**最常被漏掉的那一道防線：`state` 參數防 CSRF**。這個練習就只盯這一點：你要能說清楚「沒有 state 會怎樣」，並親手在 callback 補上驗證。
>
> 工作坊已經把 state 的完整寫法給過了。**這次請不要翻完成版**——先把它從腦中重建一次，才知道哪裡其實只是照抄沒搞懂。

---

## 題目 1：講清楚「沒有 state 會被怎麼攻擊」（觀念，用文字作答）

假設某個 callback **完全沒驗 state**，長這樣：

```js
app.get('/auth/google/callback', async (req, res) => {
  const { code } = req.query            // ← 直接拿 code 去換 token，沒檢查 state
  const token = await exchangeCodeForToken(code)
  // ...找/建使用者、簽發我們自己的 JWT...
})
```

請用 3~4 句話寫下：

- 攻擊者**如何**利用這個缺口？（提示：攻擊者先用**自己的 Google 帳號**走一次授權、攔下那組 `code`，再想辦法讓**受害者的瀏覽器**去打這個 callback。）
- 攻擊得逞後，**受害者會落入什麼狀態**？（提示：受害者在你的網站上，會被登入成**誰**的帳號？接著他新增的 todo 會進到誰的帳號裡？）
- 用一句話總結：這類攻擊的名字是什麼、`state` 為什麼能擋住它。

> 🧠 想不清楚 state 的因果鏈 → [概念卡：OAuth 2.0 授權碼流程 § state](../concepts/oauth-流程.md)

## 題目 2：親手把 state 驗證補回 callback

把上面那段「沒驗 state」的 callback 補成安全版本。要求：

- callback 從 `req.query` 同時取出 `code` **和** `state`。
- 取出先前存在 cookie 的 `oauth_state`（工作坊用 `cookie-parser`，從 `req.cookies` 讀）。
- **缺 state**、或 **state 與 cookie 裡的值不一致**時，回 **403** 並附一段 JSON 錯誤訊息——而且要在換 token **之前**就擋掉。
- 驗過之後，**清掉**這個一次性的 `oauth_state` cookie，再往下換 token。

> ⚠️ 順序很重要：驗 state 必須在「拿 code 換 token」**之前**。先換 token 再驗，等於白驗。
>
> 💡 產生 state 的那一端（`GET /auth/google`：`crypto.randomBytes`、`res.cookie('oauth_state', ...)`）工作坊已經寫好，這題只補 **callback 端的驗證**。

## 題目 3：想一想——cookie 的 `sameSite` 與 `maxAge`（觀念，用文字作答）

工作坊存 state 時寫了 `{ httpOnly: true, sameSite: 'lax', maxAge: 5 * 60 * 1000 }`。用 1~2 句話各回答：

- 為什麼這個 cookie 要設**短**的 `maxAge`（例如 5 分鐘），而不是放著不過期？
- `httpOnly` 在這裡的作用是什麼？（提示：誰**不該**能用 JS 讀到這個 state？）

## 自我檢核

把完成版（或你補好的版本）跑起來，**手動走一次** Google 登入流程來驗證：

```bash
cd 完成版
npm install
cp .env.example .env       # 填入 Google 憑證、DATABASE_URL、JWT_SECRET
npm run generate && npm run migrate
npm run dev
```

1. 瀏覽器開 `http://localhost:3000/auth/google`，被導到 Google 前，**看一眼網址列**——確認 query 裡帶了 `state=...`。
2. 正常授權走完，確認導回 callback 後拿到 `{ token, user }`（state 相符的快樂路徑）。
3. **故意改壞 state**：授權回來、callback 還沒送出前，把網址裡的 `state` 參數改掉幾個字再送出（或用工具重打一個 state 不符的 callback）。確認被回 **403**。

- [ ] 1. 導向 Google 的網址帶有 `state=...`
- [ ] 2. state 相符時，流程能跑通拿到 `{ token, user }`
- [ ] 3. 改壞 state 後重打 callback，會被回 **403**（證明驗證真的擋住了）
- [ ] 題目 1 你寫得出「攻擊者塞自己的 code → 受害者被登入成攻擊者 → 這是 CSRF，state 讓偽造的回呼對不上 cookie 而被擋」這條因果鏈
- [ ] 題目 2 你的驗證寫在「換 token **之前**」，且驗過後有 `clearCookie`

> 第 3 條（改壞 state 被擋）跑出 403 + 答得出題目 1，代表你抓到了 OAuth 流程裡最容易被忽略、卻最關鍵的那道防線。
