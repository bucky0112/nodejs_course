# 課堂練習：親手寫 requireAuth，並戳破一個安全漏洞

> 這章的核心重點不是「會用 jwt 套件」，而是**驗章（verify）≠ 解碼（decode）**、payload 是明文、以及為什麼要固定 algorithms。這個練習就針對這幾點。
>
> 工作坊已經給過 `requireAuth` 的完整程式碼。**這次請不要翻完成版**——憑理解自己寫一遍，才知道哪裡其實沒搞懂。

---

## 題目 1：從頭寫出 `requireAuth`

把 `src/middleware/requireAuth.js` 清空，自己重寫一個。要求：

- 從 `Authorization` header 取 token，格式是 `Bearer <token>`。
- 沒有 header、或開頭不是 `Bearer `，回 **401**。
- 用 `jwt.verify` 驗章（**不是** `jwt.decode`），並**明確指定** `algorithms: ['HS256']`。
- 驗過：把使用者 id 放進 `req.userId`，呼叫 `next()`。
- 驗不過（無效、過期、被竄改）：回 **401**。

> 🧠 為什麼一定要 `verify`、為什麼非寫 `algorithms` 不可？→ [概念卡：JWT 是什麼 § 兩個致命陷阱](../concepts/jwt-是什麼.md)

---

## 題目 2：加一個 `GET /auth/me`

新增一個路由，讓登入者可以查「我是誰」：

- 掛上你剛寫的 `requireAuth`。
- 用 `req.userId` 去資料庫撈出使用者。
- 回傳 `{ id, username }`——**絕對不要**把 `passwordHash` 也回出去。

---

## 題目 3（觀念，用文字作答）

某同學把 `requireAuth` 裡的這行：

```js
const payload = jwt.verify(token, process.env.JWT_SECRET, { algorithms: ['HS256'] })
```

改成了：

```js
const payload = jwt.decode(token)   // 「反正都拿得到 sub，比較快」
```

程式照跑、自己測也「正常」。請用 2~3 句話寫下：**這為什麼是嚴重的安全漏洞？攻擊者能做什麼？**

> 提示：`decode` 對 token 做了什麼、又**沒**做什麼？payload 是誰都能產生的嗎？

## 自我檢核

先登入拿一個 token，再逐條驗：

```bash
# 取得 token（換成你的帳密）
curl -s -X POST http://localhost:3000/auth/login -H "Content-Type: application/json" -d '{"username":"alice","password":"secret123"}'

# A. 帶正確 token 打 /auth/me → 應回 200 + {id, username}
curl -i http://localhost:3000/auth/me -H "Authorization: Bearer <貼上 token>"

# B. 不帶 token → 應回 401
curl -i http://localhost:3000/auth/me

# C. 竄改 token（把最後幾個字改掉）→ 應回 401
curl -i http://localhost:3000/auth/me -H "Authorization: Bearer <改壞的 token>"
```

- [ ] A. 帶有效 token 回 `200`，且回傳**不含** `passwordHash`
- [ ] B. 不帶 token 回 `401`
- [ ] C. 竄改 token 回 `401`（證明 `verify` 真的擋住了竄改）
- [ ] 題目 3 你寫得出「`decode` 不驗章，任何人都能偽造 payload」這層意思

> 三條 curl 全綠 + 答得出題目 3，代表你抓到了 JWT 最容易被誤用、也最危險的那一點。
