# 第 5 堂工作坊：把 todo API 設計成 RESTful

目前的 todo API 能列表、查單筆、新增，但還不能改、不能刪。這一堂先學 RESTful 的設計原則，再照著原則補上更新和刪除，讓整個 API 用「資源 + HTTP 方法 + 狀態碼」講出一致的話。

> 從[第 4 堂完成版](../04-middleware/完成版/)接著做。想知道「為什麼這樣寫」，每一步都有連結指向對應的[概念卡](../concepts/)。
>
> 卡住了？每個檢查點都對得上 [`完成版/`](./完成版/) 裡的程式碼，可以直接比對。

## 步驟 0：RESTful 的三個原則

**1. 網址代表「資源」，用名詞、用複數**

| 好 | 不好 |
|---|---|
| `GET /todos` | `GET /getTodos` |
| `POST /todos` | `POST /createTodo` |
| `DELETE /todos/3` | `POST /todos/3/delete` |

**2. 動作交給 HTTP 方法**

同一個網址 `/todos/3`，用不同方法表達不同動作：

| 方法 | 路徑 | 動作 |
|---|---|---|
| GET | `/todos` | 列出全部 |
| GET | `/todos/:id` | 查單筆 |
| POST | `/todos` | 新增 |
| PATCH | `/todos/:id` | 部分更新 |
| DELETE | `/todos/:id` | 刪除 |

**3. 結果交給狀態碼**

成功、前端送錯、找不到，分別用不同的狀態碼。前端不用讀錯誤訊息，看數字就知道發生什麼事。

> 🧠 CRUD 對照表、4xx 和 5xx 的差別 → [概念卡：HTTP 狀態碼](../concepts/http-狀態碼.md)

> ✅ **檢查點 A**：看到 `POST /todos/3/delete` 說得出哪裡不 RESTful、該改成什麼。

## 步驟 1：部分更新（PATCH）

在 `POST /todos` 下面加：

```js
// 部分更新 todo（PATCH：只改有送來的欄位）
app.patch('/todos/:id', (req, res) => {
  const id = Number(req.params.id)
  const todo = todos.find((t) => t.id === id)
  if (!todo) {
    return res.status(404).json({ error: '找不到這筆 todo' })
  }

  const { title, completed } = req.body ?? {}

  if (title !== undefined) {
    if (typeof title !== 'string' || title.trim() === '') {
      return res.status(400).json({ error: 'title 必須是非空字串' })
    }
    todo.title = title.trim()
  }

  if (completed !== undefined) {
    if (typeof completed !== 'boolean') {
      return res.status(400).json({ error: 'completed 必須是布林值' })
    }
    todo.completed = completed
  }

  res.json(todo)
})
```

為什麼用 **PATCH** 而不是 PUT？PUT 是「整份替換」，要送完整內容；PATCH 是「部分更新」，只送要改的欄位。我們最常做的是勾選完成，只想送 `{ "completed": true }`。

注意檢查的順序：**先確認 todo 存在（404），再檢查欄位（400）**。資源都不存在，欄位對不對就沒有意義了。

> 🧠 PUT vs PATCH 的完整比較 → [概念卡：HTTP 狀態碼 § PUT vs PATCH](../concepts/http-狀態碼.md)

```bash
curl -X PATCH http://localhost:3000/todos/1 -H "Content-Type: application/json" -d '{"completed":true}'
curl -i -X PATCH http://localhost:3000/todos/1 -H "Content-Type: application/json" -d '{"completed":"yes"}'
```

> ✅ **檢查點 B**：能把 todo 改成已完成；`completed` 給字串回 400；改不存在的 id 回 404。

## 步驟 2：刪除（DELETE）

```js
// 刪除 todo：成功回 204，沒有 body
app.delete('/todos/:id', (req, res) => {
  const id = Number(req.params.id)
  const index = todos.findIndex((t) => t.id === id)
  if (index === -1) {
    return res.status(404).json({ error: '找不到這筆 todo' })
  }
  todos.splice(index, 1)
  res.status(204).send()
})
```

刪除成功回 **204 No Content**：成功了，但沒有東西要回給你。所以用 `.send()` 而不是 `.json(...)`。

```bash
curl -i -X DELETE http://localhost:3000/todos/1   # 204
curl -i -X DELETE http://localhost:3000/todos/1   # 再刪一次：404
```

> ✅ **檢查點 C**：刪除回 204 且沒有 body；刪不存在的回 404。

## 步驟 3：整理一份 API 對照表

把整個 todo API 寫成一張表，放在 `app.js` 路由區的最上面當註解：

```js
// RESTful 路由：資源是 /todos，用 HTTP 方法表達動作
//   GET    /todos      列表         200
//   GET    /todos/:id  單筆         200 / 404
//   POST   /todos      新增         201 / 400
//   PATCH  /todos/:id  部分更新     200 / 400 / 404
//   DELETE /todos/:id  刪除         204 / 404
```

這張表就是你的 API 規格。前端拿到它，不看程式碼也知道怎麼用、會收到什麼。之後每加一個資源，都先寫出這張表再動手。

> ✅ **檢查點 D（完成版）**：表上每一列都實際打過一次，狀態碼都對得上。你的 `app.js` 應該跟 [`完成版/app.js`](./完成版/app.js) 一致。
