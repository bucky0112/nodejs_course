## 步驟 0：psql 工具箱

```bash
psql -d todo_sql
```

`psql` 裡除了 SQL，還有一組**反斜線開頭**的指令，專門用來看資料庫的狀態（它們不是 SQL，結尾不用加分號）：

| 指令 | 做什麼 |
|---|---|
| `\l` | 列出所有資料庫 |
| `\c todo_sql` | 切換到另一個資料庫 |
| `\dt` | 列出目前資料庫的所有表 |
| `\d todos` | 看 `todos` 表的結構（欄位、外鍵、index 都在這） |
| `\di` | 列出所有 index |
| `\x` | 切換「直式顯示」，欄位很多、一列太寬時好用（再打一次切回來） |
| `\timing` | 開關「每個指令花多少時間」，等一下比較 index 前後會用到 |
| `\i 檔案路徑` | 執行一個 SQL 檔（跟終端機的 `psql -f` 一樣） |
| `\?` | 所有反斜線指令的說明 |
| `\q` | 離開 |

試試看：

```
\dt
\d todos
```

`\d todos` 最下面會看到 `Indexes:`，裡面已經有一個 `todos_pkey`——**主鍵會自動建 index**，這一點等一下會用到。

> ✅ **檢查點 A**：會用 `\dt`、`\d` 看表的結構，知道 `\timing`、`\i` 是做什麼的。

## 步驟 1：交易——ROLLBACK 反悔、COMMIT 生效

第 9 堂說過：`DELETE` / `UPDATE` 下錯了就回不去。**交易（transaction）** 就是那層保險：先 `BEGIN`，中間做的事都還沒「定案」，確認沒問題才 `COMMIT`，發現不對就 `ROLLBACK`，一切回到 `BEGIN` 之前。

### 1-1 ROLLBACK：反悔

```sql
SELECT COUNT(*) FROM todos WHERE list_id = 2;   -- 先記下有幾筆（seed 資料是 2）

BEGIN;
DELETE FROM todos WHERE list_id = 2;
SELECT COUNT(*) FROM todos WHERE list_id = 2;   -- 0：在這個交易裡，資料已經不見了

ROLLBACK;                                       -- 刪錯了！撤回

SELECT COUNT(*) FROM todos WHERE list_id = 2;   -- 又回到 2
```

注意 `BEGIN` 之後提示字元會從 `todo_sql=#` 變成 `todo_sql=*#`——那個 `*` 就是在提醒你「現在在交易裡，還沒定案」。

### 1-2 COMMIT：兩件事綁在一起生效

情境：「工作」清單的兩筆 todo 做完了，要 (a) 標成完成、(b) 拿掉它們的「緊急」標籤。這兩步**要嘛都做、要嘛都不做**——只做一半的話，就會出現「已完成但還是緊急」這種怪資料。

```sql
BEGIN;
UPDATE todos SET completed = true WHERE id IN (1, 2);
DELETE FROM todo_tags WHERE todo_id IN (1, 2) AND tag_id = 1;   -- tag 1 = 緊急

-- 確認結果
SELECT t.id, t.title, t.completed, tg.name AS tag
FROM todos t
LEFT JOIN todo_tags tt ON tt.todo_id = t.id
LEFT JOIN tags tg      ON tg.id = tt.tag_id
WHERE t.id IN (1, 2);

COMMIT;   -- 沒問題 → 兩個操作一起生效
```

> 🧠 交易的原理與破壞性操作的安全習慣 → [概念卡：SQL 交易](../concepts/sql-交易.md)

## 步驟 2：交易出錯了會怎樣？兩個連線看到的一樣嗎？

### 2-1 交易裡有一句出錯

一行一行貼進 `psql`：

```sql
BEGIN;
UPDATE todos SET completed = true WHERE id = 4;
INSERT INTO todos (title) VALUES (NULL);   -- title 是 NOT NULL → ERROR
SELECT * FROM todos WHERE id = 4;          -- 也 ERROR 了！
```

第二個錯誤長這樣：

```
ERROR:  current transaction is aborted, commands ignored until end of transaction block
```

交易裡只要有一句失敗，**整個交易就壞了**，之後的指令通通被拒絕（提示字元變成 `todo_sql=!#`）。這時只能：

```sql
ROLLBACK;
SELECT completed FROM todos WHERE id = 4;   -- 還是 false：第一句 UPDATE 也一起被撤回了
```

這就是「全有或全無」：不會留下做了一半的結果。

### 2-2 兩個連線：還沒 COMMIT 的東西，別人看不到

開**兩個終端機視窗**，都 `psql -d todo_sql`，我們叫它們 A 和 B：

| 順序 | 視窗 A | 視窗 B |
|---|---|---|
| 1 | `BEGIN;` | |
| 2 | `INSERT INTO todos (title) VALUES ('A 新增的');` | |
| 3 | `SELECT title FROM todos WHERE title = 'A 新增的';` → 看得到 | |
| 4 | | `SELECT title FROM todos WHERE title = 'A 新增的';` → **看不到** |
| 5 | `COMMIT;` | |
| 6 | | 再查一次 → 看得到了 |

還沒 `COMMIT` 的改動只有自己看得到。等到 app 有很多使用者同時連進來，這個特性就很重要：別人不會讀到你做到一半的資料。

做完把這筆刪掉：`DELETE FROM todos WHERE title = 'A 新增的';`

> ✅ **檢查點 B**：做過一次 `ROLLBACK` 和一次 `COMMIT`；看過交易出錯後的 `current transaction is aborted`；知道還沒 `COMMIT` 的資料別的連線看不到。

## 步驟 3：index——先灌 10 萬筆資料

只有 6 筆 todo 的時候，怎麼查都很快，看不出 index 的差別。我們用 PostgreSQL 內建的 `generate_series` 一次灌 10 萬筆：

```sql
-- 先看看 generate_series 長什麼樣子
SELECT * FROM generate_series(1, 5);
```

它會產生 1 到 5 五列。把它接在 `INSERT ... SELECT` 後面，每個數字就變成一筆 todo：

```sql
INSERT INTO todos (title, completed, list_id, created_at)
SELECT
  '大量任務 #' || n,                 -- 大量任務 #1、大量任務 #2 ...（|| 是字串相接）
  n % 4 = 0,                         -- 每 4 筆有 1 筆已完成
  (n % 3) + 1,                       -- 平均分到 3 個清單
  now() - n * interval '1 minute'    -- 建立時間往回推，每筆差 1 分鐘
FROM generate_series(1, 100000) AS n;

ANALYZE todos;   -- 更新統計資訊，讓 PostgreSQL 知道表變大了

SELECT COUNT(*) FROM todos;   -- 100006 左右
```

> 💡 我們沒有改 `todos` 的任何欄位，只是多塞了資料。這些資料在步驟 4 結束時會刪掉。

## 步驟 4：EXPLAIN——看 PostgreSQL 打算怎麼查

在查詢前面加上 `EXPLAIN ANALYZE`，PostgreSQL 會**真的執行一次**，然後告訴你它用了什麼方法、花了多久：

```
\timing on
```

### 4-1 用標題找一筆 todo

```sql
EXPLAIN ANALYZE
SELECT * FROM todos WHERE title = '大量任務 #77777';
```

輸出很長，**只要看第一行**：

```
 Seq Scan on todos  (cost=... rows=1 ...) (actual time=... rows=1 ...)
   Filter: ((title)::text = '大量任務 #77777'::text)
   Rows Removed by Filter: 100005
   ...
 Execution Time: 3.8 ms
```

`Seq Scan`（sequential scan，循序掃描）= 從第一列看到最後一列，為了找 1 筆，丟掉了 100005 筆。

現在幫 `title` 建 index：

```sql
CREATE INDEX todos_title_idx ON todos (title);

EXPLAIN ANALYZE
SELECT * FROM todos WHERE title = '大量任務 #77777';
```

```
 Index Scan using todos_title_idx on todos  (cost=... rows=1 ...) (actual time=... rows=1 ...)
   Index Cond: ((title)::text = '大量任務 #77777'::text)
   ...
 Execution Time: 0.04 ms
```

變成 `Index Scan`：先查索引（像書後面的索引頁）直接找到那一列，不用整張表掃過去。`Execution Time` 也差了快百倍（數字每台電腦不同，看量級就好）。

> 有時候你看到的會是 `Bitmap Heap Scan` 底下接一個 `Bitmap Index Scan`，那也是有用到 index，只是取資料的方式不同。
>
> 如果看到 `Parallel Seq Scan`、`Gather`，那是 PostgreSQL 開了好幾個 worker 一起掃，本質上還是整張表掃過去的 `Seq Scan`。

### 4-2 列表頁：最新的 10 筆

todo app 的首頁通常是「最新的幾筆」：

```sql
EXPLAIN ANALYZE
SELECT id, title, created_at FROM todos ORDER BY created_at DESC LIMIT 10;
```

你會看到 `Limit` → `Sort` → `Seq Scan`：整張表讀完、全部排序，才取前 10 筆。

```sql
CREATE INDEX todos_created_at_idx ON todos (created_at);

EXPLAIN ANALYZE
SELECT id, title, created_at FROM todos ORDER BY created_at DESC LIMIT 10;
```

變成 `Index Scan Backward using todos_created_at_idx`：index 本來就是排好序的，從尾巴往回讀 10 筆就停，`Sort` 那一步不見了。

### 4-3 index 不是萬靈丹

```sql
CREATE INDEX todos_completed_idx ON todos (completed);

EXPLAIN
SELECT * FROM todos WHERE completed = false;
```

```
 Seq Scan on todos  (cost=... rows=75201 ...)
   Filter: (NOT completed)
```

有 index，PostgreSQL 卻**不用**。因為「未完成」佔了大約 3/4 的資料——要拿走大部分的列時，查索引再一筆一筆跳回表裡拿，反而比直接整張掃過去慢。PostgreSQL 的查詢規劃器會自己估算哪個便宜。

所以 index 適合「**從很多資料裡挑出少數幾筆**」的欄位。而且 index 也有成本：佔空間、每次 `INSERT` / `UPDATE` 都要順便更新它。不是每個欄位都加就好。

用 `\di` 看看我們建了哪些 index，然後收尾：

```sql
DROP INDEX todos_completed_idx;
DROP INDEX todos_title_idx;
DROP INDEX todos_created_at_idx;
DELETE FROM todos WHERE title LIKE '大量任務 #%';
ANALYZE todos;
```

> ✅ **檢查點 C**：親眼看到加 index 前是 `Seq Scan`、加 index 後是 `Index Scan`（或 `Bitmap Index Scan`）；能解釋為什麼 `completed = false` 不用 index。

## 步驟 5：正規化——先看一張「沒拆開」的表

假設當初偷懶，清單名稱直接存成字串：

```sql
CREATE TABLE demo_todos_flat (
  id        INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title     VARCHAR(200) NOT NULL,
  completed BOOLEAN NOT NULL DEFAULT FALSE,
  list_name VARCHAR(100)                 -- 清單名稱每一列都存一次
);

INSERT INTO demo_todos_flat (title, completed, list_name) VALUES
  ('寫專案週報',       true,  '工作'),
  ('修登入頁的 bug',   false, '工作'),
  ('回覆客戶信件',     false, '工做'),   -- 有人打錯字
  ('買牛奶',           false, '生活'),
  ('預約看牙醫',       false, '生活'),
  ('學會 SQL JOIN',    false, '學習');
```

> 為了不動到第 9 堂的 `lists` / `todos`，這一段的表都用 `demo_` 開頭。

看看出了什麼問題：

```sql
-- 問題 1：打錯一個字，「工作」就分裂成兩個清單
SELECT list_name, COUNT(*) FROM demo_todos_flat GROUP BY list_name;

-- 問題 2：想把「工作」改名成「公司」，要改每一列；拼錯的那列就漏掉了
UPDATE demo_todos_flat SET list_name = '公司' WHERE list_name = '工作';
SELECT title, list_name FROM demo_todos_flat ORDER BY id;
```

同一份資訊（「這個清單叫什麼」）存了好幾次，就會有「改了這裡、忘了那裡」的問題。**正規化**的核心就是：**一件事只存在一個地方**，其他地方用 id 指過去。

先把資料還原，準備拆表：

```sql
UPDATE demo_todos_flat SET list_name = '工作' WHERE list_name IN ('公司', '工做');
```

## 步驟 6：拆成兩張表，用 JOIN 拼回來

### 6-1 建兩張表

```sql
-- 「一」邊：每個清單名稱只存一次
CREATE TABLE demo_lists (
  id   INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name VARCHAR(100) NOT NULL UNIQUE
);

-- 「多」邊：只存清單的 id（外鍵）
CREATE TABLE demo_todos (
  id        INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title     VARCHAR(200) NOT NULL,
  completed BOOLEAN NOT NULL DEFAULT FALSE,
  list_id   INT REFERENCES demo_lists(id) ON DELETE SET NULL
);
```

眼熟嗎？這就是第 9 堂的 `lists` + `todos`。`name` 加了 `UNIQUE`，同一個名稱不可能存兩次。

### 6-2 把舊資料搬過去

```sql
-- 不重複的清單名稱 → demo_lists（ORDER BY MIN(id)：照第一次出現的順序編號）
INSERT INTO demo_lists (name)
SELECT list_name
FROM demo_todos_flat
WHERE list_name IS NOT NULL
GROUP BY list_name
ORDER BY MIN(id);

-- 用名稱 JOIN 找到對應的 id → demo_todos
INSERT INTO demo_todos (title, completed, list_id)
SELECT f.title, f.completed, l.id
FROM demo_todos_flat f
LEFT JOIN demo_lists l ON l.name = f.list_name
ORDER BY f.id;

SELECT * FROM demo_lists;
SELECT * FROM demo_todos;
```

`demo_todos` 裡已經沒有清單名稱，只剩 `list_id` 這個數字。

### 6-3 用 JOIN 拼回原本的樣子

```sql
SELECT t.title, t.completed, l.name AS list_name
FROM demo_todos t
LEFT JOIN demo_lists l ON l.id = t.list_id
ORDER BY t.id;
```

結果跟原本的 `demo_todos_flat` 一樣——資料拆開存，查的時候用 JOIN 拼回來，這就是第 9 堂學 JOIN 的理由。

### 6-4 好處：改名只改一個地方

```sql
UPDATE demo_lists SET name = '公司' WHERE name = '工作';   -- UPDATE 1，只動 1 列

-- 再跑一次 6-3 的 JOIN：三筆工作的 todo 全部變成「公司」
```

外鍵還會擋掉不合理的資料，試試看（會出現 ERROR）：

```sql
INSERT INTO demo_todos (title, list_id) VALUES ('孤兒 todo', 999);
```

> 🧠 1:N 為什麼外鍵放在「多」邊、`ON DELETE` 的選項 → [概念卡：SQL 關聯與 JOIN](../concepts/sql-關聯與join.md)
>
> ✅ **檢查點 D（完成版）**：你的 `demo_lists` / `demo_todos` 與 [`完成版/normalization.sql`](./完成版/normalization.sql) 建出來的一致，JOIN 拼回來的結果跟 `demo_todos_flat` 對得起來。
